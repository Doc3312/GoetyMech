# Auto-sprint：客户端 START_SPRINTING 包注入才是正确方案

status: verified

## 问题

原型冲刺和跑墙容易断连。长按 W 不按 Ctrl 时，跑一小段就变回走。

## 尝试过的方案（已废弃）

### 方案 A：服务端 `movedXZ` 恢复

在 `PrototypeEvents.onPlayerTick()` END phase 用 `getX() - xo` 检测水平位移，超过阈值则 `setSprinting(true)`。

**废弃原因**：
- 服务端 `getX() - xo` 不反映客户端实际移动（`docs/incidents/_craft/20260710.slam-freeze-craterblock.md` 教训 #2）
- 在位置不同步场景（slam freeze、碰撞校正）下，服务端 `moved = 0`，恢复失效

### 方案 B：服务端 `player.zza` 检测

在 `PrototypeEvents.onPlayerTick()` 中使用 `player.zza > 0` 判断前进意图。

**废弃原因**：
- `ServerPlayer.setPlayerInput()` 仅当 `isPassenger()` 为真时写入 `zza`。对步行玩家什么都不做
- `LivingEntity.aiStep()` 服务端走 `serverAiStep()` 也不设 `zza`
- 服务端 `player.zza` 恒为 0（`docs/incidents/_meta/20260623.charge-jump-sprint-inertia.md` 已有记录）

## 真实方案：客户端 START_SPRINTING 包注入

`PrototypeRenderEvents.onClientTick()` START 阶段检测：

```
持有原型 + 按住 W + 未按冲刺键 + 未冲刺 + 在地面
+ 未潜行 + 未飞行 + 非墙跑 + 食物 > 6
→ mc.player.connection.send(START_SPRINTING packet)
→ player.setSprinting(true)  // 本地立即同步
→ autoSprintCooldown = 10    // 防震荡
```

### 为什么这是正确方案

| 问题 | 方案 A `moved` | 方案 B `zza` | 方案 C（最终）`START_SPRINTING` |
|------|---------------|-------------|-------------------------------|
| 服务端位置不同步 | ❌ `moved=0` 失效 | N/A | ✅ 客户端本地判断意图 |
| `zza` 服务端恒为 0 | N/A | ❌ 永远 false | ✅ 绕开服务端输入检测 |
| 需要新 C2S 包 | N/A | N/A | ❌ 不需要，用 vanilla 现有机制 |
| 兼容 toggle-sprint | ✅ 无干扰 | ✅ 无干扰 | ✅ 仅在需要时发包 |

### 关键要点

1. **用 `Minecraft.getConnection()` 而非 `LocalPlayer.connection`** — 后者在某些 mappings 中名命不同，`getConnection()` 是 Parchment 稳定的 API
2. **10 tick cooldown** 防止服务端同 tick 再次取消 sprint（如食物刚好 ≤6 的边界情况）
3. **本地也调 `player.setSprinting(true)`** — 确保当前 tick 的 wall run 检测（`PrototypeRenderEvents.java:94` 的 `sprinting` 变量）能立即看到 sprint 状态，无需等服务端回传
4. **仅在 `!ClientWallRunState.isActive()` 时发** — 墙跑时 MixinWallRunTravel 已在设 `setSprinting(true)`，避免冗余包
