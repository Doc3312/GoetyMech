## 根因

### Phase 1：怀疑 slamFreezeTick 系统

slamFreezeTick 每 tick 在 `onLivingTick` 和 `onPlayerTick START` 中归零 velocity、清 xxa/yya/zza。

**措施**：删除全部三处冻结代码 + NBT tag。

**结果**：仍然被困。说明根因不在这里。

### Phase 2：怀疑残留动量

SLAM_DIAG 日志显示服务端 `dm=(0, -0.0784, 0)` 持续 40 tick，`movedXZ=0`。客户端 SLAM_DIAG_CLIENT 显示 `input=(fwd=true)` 且 `movedXZ=0.025`。

**措施**：加 `SLAM_ZERO_H` 清零服务端水平动量 + `hurtMarked` 同步。

**结果**：更糟。清零导致服务端-客户端动量不一致，客户端被拉回更严重。

### Phase 3：怀疑地面起飞

用户报告"不按 W 也抽动" — 排除地面起飞代码（需要 zza>0）。

### Phase 4：CraterBlock 替换

用户发现"被惯性带飞出塌陷范围（6格）就能正常跑，范围内就不能动"。

**根因**：`SlamGroundTiltHandler.startEffect()` 在客户端把半径 6 格内的方块替换为 `CraterBlock`（`.noCollission()`、`Shapes.empty()`）。客户端脚下方块被挖成空气 → 客户端玩家往下掉 → 服务端仍有原始方块 → 拉回 → 每 tick 循环。飞行能跑因为不依赖地面碰撞。

### Phase 5：CraterBlock 碰撞箱修复

**修复**：`CraterBlock.getCollisionShape()` 返回原始方块的碰撞箱（`orig.getCollisionShape(level, pos, ctx)`），而非 `Shapes.empty()`。这样客户端方块被替换后碰撞箱不变，玩家不会掉下去。倾斜/旋转动画照常渲染。

## 修复

- `common/block/CraterBlock.java` — getCollisionShape 修复
- `client/SlamGroundTiltHandler.java` — 方块替换逻辑
- `common/net/s2c/S2CSlamImpactPacket.java` — 触发客户端效果
- `common/block/entity/CraterBlockEntity.java` — 存储原始方块状态

## 经验提炼

| # | 教训 |
|---|------|
| 1 | BESR 视觉方块（CraterBlock）设置 `.noCollission()` 会导致客户端玩家站不住 → 服务端拉回 → 抽动。视觉方块应有与原始方块一致的碰撞箱 |
| 2 | 服务端 `player.zza` 永远为 0，服务端测得的 `movedXZ` 不反映客户端实际移动。诊断必须加客户端侧输入和位置追踪 |
| 3 | 使用 `level.setBlock()` 替换客户端方块做视觉效果时，必须考虑替换后对玩家碰撞的影响 |
