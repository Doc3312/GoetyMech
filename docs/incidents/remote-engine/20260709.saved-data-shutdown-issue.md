# 存档保存/加载问题深度分析与修复

## 问题概述

重进存档后，Ark GUI 显示 0/0，绑定关系丢失，引擎无法正常工作。

## 问题根因

### 根因1：服务器关闭时数据被覆盖（最关键）

**问题流程**：

1. 服务器保存世界时，第一次 `save(File)` 被调用，此时 `bindings=2`（正确数据）
2. 服务器继续关闭，`invalidate()` 被调用 → `unbind()` 删除绑定 → `markDirty()` 把数据标记为脏（bindings=0）
3. 服务器第二次调用 `save(File)`，此时 `isDirty=true`，用空数据覆盖了第一次保存的正确数据

**日志证据**：
```
358: [save(File)] called, isDirty=true, bindings=2, owners=1  ← 第一次保存：数据正确！
391: [save(File)] called, isDirty=true, bindings=0, owners=0  ← 第二次保存：数据被清空！
```

**修复方案**：添加 `shuttingDown` 标志，在 `ServerStoppingEvent` 中设置，阻止 `markDirty()` 在关闭期间执行。

### 根因2：引擎加载时触发 unbind

**问题流程**：

1. `levelLoaded()` 加载数据
2. 引擎加载时，`updateFromNetwork` 被调用，触发 `onEngineNetworkChanged`
3. 如果引擎不在网络中（networkSize=0），会触发 `unbind()`，删除绑定关系

**修复方案**：添加 `loading` 标志，在 `levelLoaded()` 期间跳过 `unbind()`。

### 根因3：初始化时机太晚

**问题流程**：

1. 之前使用 `ServerTickEvent` 延迟初始化，导致 `levelLoaded()` 在第一个 ServerTick 才被调用
2. 此时引擎可能已经加载，触发了 `unbind()`

**修复方案**：在 `LevelEvent.Load` 中直接调用 `levelLoaded()`，遵循 Create 的模式。

### 根因4：缓存填充时机不对

**问题流程**：

1. `onReaderLoad()` 在 Reader 加载时填充缓存
2. 但此时 Reader 的网络数据（capacity、stress）可能还未从 Create 的网络更新
3. 缓存被填充为初始值（0），导致 Ark 显示 0/0

**修复方案**：不在 `onReaderLoad()` 中填充缓存，只在 `onReaderNetworkChanged()` 中填充。

### 根因5：Ark HUD 不消失

**问题流程**：

1. 破坏 Ark 时，`onArkRemoved()` 没有被调用
2. 客户端缓存的旧数据仍然存在，导致 HUD 显示

**修复方案**：添加 `PlayerLoggedInEvent` 监听，登录时检查是否有活动 Ark，若无则发送清除包。

## 错误修复方案记录（踩过的坑）

### 错误方案1：添加 loadTickDelay 延迟初始化

**假设**：问题是初始化时机太早，网络数据还没准备好

**方案**：在 `tick()` 中设置 `loadTickDelay = 10`，等待10个tick后再填充缓存和触发 `distributeBudget()`

**结果**：数据文件还是空的，因为 `save(File)` 在延迟期间被调用，保存了空数据

**为什么错**：问题不是初始化时机，而是数据在保存前被清空了

---

### 错误方案2：在 onReaderLoad() 中填充缓存

**假设**：问题是缓存没有被填充

**方案**：在 `onReaderLoad()` 中用初始值（0）填充缓存

**结果**：覆盖了真实数据，导致显示 0/0

**为什么错**：缓存应该在网络数据更新后才填充，而不是在 Reader 加载时

---

### 错误方案3：在 loadStressLinkData() 中填充缓存

**假设**：问题是缓存没有在加载时填充

**方案**：在 `loadStressLinkData()` 中遍历所有 Reader 填充缓存

**结果**：Reader 的网络数据还没更新，填充了初始值（0）

**为什么错**：加载时网络数据还没从 Create 更新，此时填充的是初始值

---

### 错误方案4：在 tick() 中延迟触发 distributeBudget()

**假设**：问题是分配预算太早

**方案**：延迟10个tick后再触发分配

**结果**：绑定关系在延迟期间被删除了

**为什么错**：绑定关系被删除不是因为分配太早，而是因为 `invalidate()` 被调用

---

### 错误方案5：修改 save() 方法返回新的 CompoundTag

**假设**：问题是 `save()` 方法没有正确返回数据

**方案**：修改 `save()` 方法返回新创建的 CompoundTag

**结果**：问题依旧，因为根本原因是数据被清空后才保存

**为什么错**：`save()` 方法本身没有问题，问题是数据在保存前被清空了

### 错误方案6：重写 save(File) 方法

**假设**：问题是 `save(File)` 方法没有正确写入数据

**方案**：使用 Create 的 `SavedDataUtil.saveWithDatOld()`

**结果**：问题依旧，因为数据在保存前就被清空了

**为什么错**：`save(File)` 方法本身没有问题，问题是数据在保存前被清空了

---

### 错误方案7：在 onEngineLoad() 中重新绑定

**假设**：问题是引擎加载时没有恢复绑定

**方案**：在 `onEngineLoad()` 中检查存档中的绑定关系并重新绑定

**结果**：数据文件为空，没有绑定关系可以恢复

**为什么错**：数据文件为空是因为之前的数据没有被正确保存，而不是绑定关系没有被恢复

**假设**：问题是 `savedData` 没有被初始化

**为什么错**：`savedData` 初始化没有问题，问题是数据在保存前被清空了

private boolean shuttingDown = false;

public void onServerStopping() {
    shuttingDown = true;
}

public void markDirty() {
    if (shuttingDown) return;  // 关闭期间不标记脏数据

    }

## 经验教训

### 教训1：服务器关闭时的数据保护

服务器关闭时，`invalidate()` 会被调用，导致数据被修改。如果此时 `markDirty()` 被调用，第二次 `save(File)` 会覆盖第一次保存的正确数据。

**解决方案**：在 `ServerStoppingEvent` 中设置标志，阻止 `markDirty()` 在关闭期间执行。

### 教训2：初始化时机的重要性

初始化时机太晚会导致引擎加载时触发 `unbind()`，删除绑定关系。

**解决方案**：在 `LevelEvent.Load` 中直接调用 `levelLoaded()`，遵循 Create 的模式。

### 教训3：缓存填充时机的重要性

缓存填充时机不对会导致缓存被填充为初始值（0），导致显示错误。

**解决方案**：不在 `onReaderLoad()` 中填充缓存，只在 `onReaderNetworkChanged()` 中填充。

### 教训4：多保存点的问题

Minecraft 服务器在关闭时会保存多次，第一次保存正确数据，第二次保存可能会覆盖。

**解决方案**：确保第二次保存时数据没有被修改，或者阻止第二次保存覆盖第一次的数据。

### 教训5：测试代码的重要性

添加详细的日志输出是定位问题的关键。通过日志可以清晰看到数据的变化过程，找到问题的根因。

**解决方案**：在关键方法中添加日志输出，记录数据的变化过程。

### 教训6：不要假设，要验证

之前的所有错误方案都是基于错误的假设，没有通过日志验证。应该先添加详细日志，观察数据的变化过程，再制定修复方案。

**解决方案**：在关键方法中添加日志输出，记录数据的变化过程，然后根据日志分析问题。

## 验证结果

修复后，日志显示：
```
[onServerStopping] shuttingDown=true, bindings=3          ← 关闭前有3个绑定
[unbind] markDirty SKIPPED during shutdown                ← 不再标记脏数据
[save(File)] called, isDirty=false, bindings=0, ...       ← 第二次保存发现isDirty=false，不覆盖
```

第二次 `save(File)` 时 `isDirty=false`，意味着不会再覆盖第一次保存的正确数据。
