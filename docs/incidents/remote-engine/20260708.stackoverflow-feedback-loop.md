## 根因

### 死循环链路

```
pushToEngine (L210)
  → engine.applyRemoteUpdate
    → updateGeneratedRotation
      → [speed!=0 && hasNetwork] notifyStressCapacityChange + updateStressFor + updateStress
        → engine 网络 sync() → updateFromNetwork
          → RemoteEngineBlockEntity.updateFromNetwork → onEngineNetworkChanged
            → reader.setRemoteEngineConsumption
              → reader 网络 updateStressFor → updateStress → sync
                → reader updateFromNetwork → onReaderNetworkChanged
                  → pushToEngine ← 回到起点，无限递归
```

### 关键发现：updateGeneratedRotation 无条件触发 sync

`GeneratingKineticBlockEntity.updateGeneratedRotation()` 中：

```java
if (hasNetwork() && speed != 0) {
    notifyStressCapacityChange(calculateAddedStressCapacity());
    getOrCreateNetwork().updateStressFor(this, calculateStressApplied());
    network.updateStress();
}
```

这段代码**无论 speed 是否变化都会执行**（只要 speed != 0 且有网络）。即使 `prevSpeed == speed`（不调用 `applyNewSpeed`），只要引擎在运转，每次调用 `updateGeneratedRotation` 都会触发 engine 网络的 `updateStress()` → `sync()`。

`sync()` 同步遍历所有 members 调用 `updateFromNetwork`，而 `RemoteEngineBlockEntity.updateFromNetwork` 覆盖了，会调用 `onEngineNetworkChanged` → `setRemoteEngineConsumption` → reader 网络 sync → `onReaderNetworkChanged` → 又 `pushToEngine` → 又 `applyRemoteUpdate` → 又 `updateGeneratedRotation` → ...

整个调用链是**同步递归**的，同一 tick 内无限递归 → StackOverflowError。

### 为什么单引擎不崩溃

单引擎时，第一次 push 后数值立即收敛：
- push 设置 budget → engine capacity = budget
- engine 网络 sync → onEngineNetworkChanged → setRemoteEngineConsumption(X)
- reader 网络 sync → onReaderNetworkChanged → 第二次 push
- 第二次 push 的 budget 跟第一次相同（数学等价，见下文）→ capacity 不变 → updateStress 短路 → 不触发 sync → 循环断开

但多引擎时，第二个引擎的加入改变了 totalConsumption，导致 reader stress 变化，进而改变所有引擎的 budget，每轮 push 都有数值变化，递归不收敛。

## 修复

修复后，第二轮 push 的 budget 与第一轮数学等价：

```
budget1 = C - oldReaderStress + oldEngineStress
budget2 = C - newReaderStress + newEngineStress

newReaderStress = oldReaderStress - oldEngineStress + newEngineStress  (total consumption 变化)

代入：
budget2 = C - (oldReaderStress - oldEngineStress + newEngineStress) + newEngineStress
        = C - oldReaderStress + oldEngineStress
        = budget1
```

因此第二轮 push 时 `calculateAddedStressCapacity()` 返回值不变 → capacity 不变 → `updateCapacity` 短路。stress 也不变 → `updateStress` 短路。engine 网络不 sync → `onEngineNetworkChanged` 不触发。`setRemoteEngineConsumption(total)` 中 total 不变 → 短路。循环断开。

## 经验提炼

| 教训 | 说明 |
|------|------|
| **Create 的 sync 是同步递归的** | `sync()` 同步遍历 members 调用 `updateFromNetwork`，任何在 `updateFromNetwork` 中触发的网络更新都会形成递归 |
| **updateGeneratedRotation 无条件触发网络更新** | 即使 speed 不变，只要 speed!=0 && hasNetwork，就会调用 `notifyStressCapacityChange` + `updateStressFor` + `updateStress` |
| **双向反馈回路必须有重入防护** | Reader→Engine (push) 和 Engine→Reader (onEngineNetworkChanged) 两个方向都会触发网络 sync，必须在至少一个方向加 suppress 标志 |
| **短路检查是收敛的关键** | `KineticNetwork.updateStress/updateCapacity` 的值变化短路 + `setRemoteEngineConsumption` 的 Float.compare 短路，两重短路确保数值收敛后循环断开 |
| **budget 公式必须加回自身消耗** | `getNetworkStress()` 包含所有引擎消耗，不加回当前引擎消耗会导致双重计入，budget 被过度压缩 |
| **过载振荡是物理真实的** | 当 engine 消耗 > budget 时，overStressed 状态会切换，但 `calculateStress()` 用 theoreticalSpeed，stress 值不变，不会形成振荡。振荡只发生在 budget 变化导致 capacity 变化时 |
