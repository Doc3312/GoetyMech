# Auto-pool 复杂度死亡螺旋 — 最终删除

status: verified

## 背景

Remote Engine 的 auto-pool 功能试图实现：引擎自动注册到一个玩家池，StressArk 自动分配给绑定引擎。但这引入了多层脆弱的耦合，经过 P0-P5 五轮修复仍无法稳定工作。

## 问题链

1. **budget 过度分配** — `calculateAddedStressCapacity()` 返回全量，Create 网络做 capacity 求和后翻倍
2. **引擎注册时机** — `setPlacedBy()` 设 placerUUID，但 BE 可能尚未 fully loaded → readerCache 为空 → skip auto-bind
3. **readerCache fallback** — 为了解决时机问题，加了 `onReaderLoad()` 缓存 → 引入并发读取问题
4. **跨存档泄漏** — SavedData 不随 level unload 清空 → 新存档读到旧存档的数据
5. **EngineStatus 状态机** — 多了一个状态枚举，难以对齐实际 tick 时序

## 教训

| 教训 | 说明 |
|------|------|
| **1:1 binding > auto-pool** | 用户手动绑定/解绑比自动注册更可靠，减少耦合面 |
| **事件驱动 > 轮询** | `updateFromNetwork()` override 比 20tick 缓存更精确 |
| **SavedData 必须清理** | 全局 SavedData 要在 level unload 时 `clear()`（通过独立 event handler 类） |
| **不要修改原型代码** | PrototypeEvents.java 的修改需要来回 revert，应开独立事件类 |
| **功能膨胀 → revert** | 如果 5 轮修复后仍不稳定，应回退到已知正确的最小实现 |

## 当前状态

Auto-pool 完全删除。系统退回到纯 1:1 binding（匹配 EnderTransmission 模式），无消耗追踪、无状态机。
