# 应力系统重构方案 — StressLink

> 方案号: S-2026-001
> 状态: 草案
> 作者: opencode
> 参考: CreateEnderTransmission (1.20.1), Create-Stressbound (1.21.1)

---

## 1. 当前架构的根因问题

### 问题一：StressReader 错误地成为了应力消费者

`StressReaderBlockEntity` 继承 `KineticBlockEntity` 并重写 `calculateStressApplied()`：

```java
public float calculateStressApplied() {
    float consumed = getConsumedRemotely();
    return consumed / speed;  // Reader 在消耗应力！
}
```

**后果**：Reader 在自己的网络上表现为一个负载。当 RemoteEngine 和 Reader 的 Create 网络有重叠时，产生反馈循环：Engine 注入容量 → 网络总容量变 → Reader 看到变化 → 分配变化 → Engine 重新计算 → 循环。

**正确做法**：Reader 应只监控不消耗，不重写 `calculateStressApplied()`。

### 问题二：全局静态状态替代了服务层

```
StressReaderBlockEntity.ACTIVE_READERS    → Set<ReaderBE>（全局静态，跨越所有维度）
StressReaderBlockEntity.NETWORK_UPDATED    → static volatile boolean
StressArkBlockEntity.PLAYER_ACTIVE_ARK     → static Map<UUID, ArkLocation>
```

**后果**：
- 两个不相关玩家在同一服务器上互相污染数据
- 所有维度的 Reader 混在一个 Set 中，Ark 的扫描无隔离
- 存档重载后 `PLAYER_ACTIVE_ARK` 丢失（静态不持久化）
- 多线程下 `synchronized` 锁争用（所有 Ark 竞争 ACTIVE_READERS）

### 问题三：缓存值镜像替代了实时传播

RemoteEngine 每 20 tick 从 Reader/Ark 读取 RPM 和容量，存入 `cachedRpm` 和 `cachedConsumed`，然后通过 `getGeneratedSpeed()` 和 `calculateAddedStressCapacity()` 返回。

**后果**：
- RPM 是快照值，不是实时传播
- Create 的 `KineticNetwork` 不知道远程连接的存在
- 应力变化在 1 秒后才反映到 Engine 上

### 问题四：Ark 的自动扫描无隔离

Ark 的 `getRepresentativeRPM()` 从 `ACTIVE_READERS` 全局 Set 中遍历，选出可用应力最大的 Reader 的 RPM。多个 Ark 同时扫描同一个 Set，必然导致:
- 数据混乱（A 玩家的 Ark 读到了 B 玩家的 Reader）
- RPM 随机漂移（扫描到不同的 Reader 返回不同的 RPM）

## 2. 重构目标

| # | 目标 | 优先级 |
|---|------|--------|
| 1 | 消除所有的全局静态状态 | P0 |
| 2 | Reader 不再消耗应力（停止重写 `calculateStressApplied()`） | P0 |
| 3 | 用事件驱动替代周期性缓存刷新（Reader `updateFromNetwork()` → 即时推送） | P0 |
| 4 | 引入持久化的链路服务层（`SavedData`） | P1 |
| 5 | 修复 Ark 自动扫描的隔离性（按玩家 UUID 过滤，不再跨玩家污染） | P1 |
| 6 | 保持双向兼容：StressFocus、StressShieldFocus 等外部调用不受影响 | P1 |
| 7 | 代码量控制在 15 个 Java 文件以内（当前 16 个） | P2 |

## 3. 新架构设计

### 3.1 组件角色重新定义

```
┌──────────────────────────────────────────────────────────┐
│                    StressLinkService                      │
│  (服务层, SavedData 持久化, 事件驱动更新)                  │
│  - 管理所有 Reader↔Engine / Reader→Ark→Engine 链路        │
│  - Reader 网络变化时即时 recalc + push 给 Engine          │
└────────────────────┬─────────────────────────────────────┘
                     │ push(speed, budget)
         ┌───────────┴───────────┐
         ▼                       ▼
  StressReader             RemoteEngine
  (监控, 不消耗)            (GeneratingKBE, 从push接收)
  - remove ACTIVE_READERS   - remove 缓存
  - remove calculateStressApplied()  - remove 双模式(ARK/READER)
  - hook updateFromNetwork()        - 仅 Keep 1:1 绑定
  ↓                              ↑
  StressArk (玩家隔离的自动扫描)
  - 仍自动发现 Reader，但通过 Service 按 ownerUUID 过滤
  - 只看到同玩家的 Reader，不跨玩家污染
  - Ark 从 Service 读取按玩家聚合的数据
```

### 3.2 数据模型

```java
// StressLinkSavedData.java (extends SavedData)
class StressLinkSavedData {
    // 1:1 绑定: RemoteEngine → StressReader
    Map<GlobalBlockPos, DirectBinding> directBindings;
    
    // Ark 绑定: StressArk → 组
    Map<GlobalBlockPos, ArkGroup> arkGroups;
    
    // 反向索引: ReaderPos → 哪些 Engine 依赖它
    // （用于 updateFromNetwork() 触发时快速找到受影响 Engine）
    Map<GlobalBlockPos, Set<EngineRef>> readerDependents;
    
    record DirectBinding(GlobalBlockPos readerPos);
    
    record ArkGroup(
        UUID ownerUUID,
        List<GlobalBlockPos> readerList,
        List<GlobalBlockPos> engineList
    );
    
    record GlobalBlockPos(ResourceKey<Level> dimension, BlockPos pos);
}
```

### 3.3 事件驱动流程

```
Create 网络变化
   ↓
StressReader.updateFromNetwork(capacity, stress, size)
   ↓  override: 如果 capacity 或 stress 变化
StressLinkService.onReaderChanged(readerPos, capacity, stress)
   ↓
查找 readerDependents[readerPos] → 所有关联 Engine
   ↓
对每个 Engine:
  speed = reader.getSpeed()
  budget = capacity - stress (或比例分配)
  push(speed, budget) → Engine.updateExternal(speed, budget)
   ↓
RemoteEngine.updateGeneratedRotation()
   ↓
Create 网络重新计算
```

### 3.4 绑定流程

**1:1 绑定（Engine ↔ Reader）**

```
玩家手持 RemoteEngineBlockItem → 右键 StressReader
  → Item NBT 写入 boundPos = readerPos
  → 放置 RemoteEngine 时
    → RemoteEngineBlockEntity.initialize()
    → 从 Item NBT 读 boundPos → 注册到 StressLinkService
    → Service 记录 directBindings[enginePos] = readerPos

玩家 Shift+右键 Reader（手持 Engine item）
  → 解绑 → Service 移除条目
  → Engine 停转
```

**Ark 绑定（Reader → Ark → Engine）**

```
玩家放置 Ark
  → Ark 注册到 Service，附 ownerUUID
  → Service 自动发现同玩家的所有 Reader（从 ReaderRegistry 中过滤）
  → Ark 自动聚合这些 Reader 的可用应力

玩家放置 Engine
  → Engine 自动绑定到最近的同玩家 Ark（或通过工具指定）
  → Service 在 Ark 的引擎列表中注册
  → 每次 Reader 网络变化 → Service recalc → push 给所有引擎
```

## 5. 可行性评估

### 5.1 技术可行性 ✅

所有使用的 API 都是 Create 和 Minecraft Forge 提供的公开 API：

| 依赖 | 是否公开 | 说明 |
|------|----------|------|
| `KineticBlockEntity.updateFromNetwork()` | `protected` | 可 override |
| `GeneratingKineticBlockEntity` | 公开 | 无变化 |
| `SavedData` | 公开 | 标准实现 |
| `updateGeneratedRotation()` | 公开 | 触发网络重新计算 |
| Forge Config | 公开 | 已有使用 |

### 5.2 兼容性影响

| 功能 | 影响 |
|------|------|
| StressFocus → CrushingWheelSpell | **无影响**。直接调用 Reader 的 `getNetworkCapacity()`/`getNetworkStress()`，这些方法保留 |
| StressShieldFocus → StressShieldSpell | **轻微影响**。改用 Service API 替代 `getActiveArkPos()` |
| Existing Ark in-world (存档迁移) | **需要迁移逻辑**。Service 首次加载时读取旧 Ark 的 NBT |
| Existing Engine in-world (存档迁移) | **需要迁移逻辑**。旧 NBT 有 `bindingType`、`ArkPos`、`LinkedPos` 等字段 |
| 连线渲染 (ModClientForgeEvents) | **无影响**。渲染基于 BE 状态，不直接依赖 Service |
| 应力注册配置 (`ModBlocks.registerStressValues`) | **需要调整**。Reader 的 IMPACT 必须从当前值改为 0 |

### 5.3 存档迁移策略

Service 的 `load()` 方法在首次加载时扫描所有已加载的块实体，识别旧的 `StressReaderBlockEntity` 和 `RemoteEngineBlockEntity`，从它们的 NBT 中提取绑定信息并转换为新的数据模型。一次性的迁移逻辑，后续不再需要。

## 6. 优缺点

### 优点

| # | 优点 |
|---|------|
| 1 | **消除反馈循环** — Reader 不再消耗应力，Engine 注入和 Reader 读取不再互相干扰 |
| 2 | **实时响应** — `updateFromNetwork()` 是 Create 原生回调，网络变化即时触发推送 |
| 3 | **无全局静态** — 所有状态在 Service 中，可持久化、可恢复、维度隔离 |
| 4 | **引擎不再抖动** — 移除周期性缓存刷新，Engine 转速不再每 20 tick 跳跃 |
| 5 | **逻辑简化** — 移除双模式（ARK/READER）、移除分布式消耗计算 |
| 6 | **代码量少** — 13 个文件 vs 当前 16 个，新增 4 个但删除 2 个、重写 4 个 |

### 缺点

| # | 缺点 | 缓解措施 |
|---|------|----------|
| 1 | **存档迁移** — 旧世界的 Ark/Engine NBT 格式与新格式不同 | 一次性迁移逻辑，读旧 NBT 转新模型 |
| 2 | **`updateFromNetwork()` 不是保证调用的** — Create 只在网络变化时触发，冷启动时 Engine 可能延迟 | 在 Service 首次加载 + Engine `initialize()` 时主动查询一次 |
| 4 | **新增 Service 依赖** — BE 之间存在间接引用 | Service 是唯一中心节点，不涉及循环依赖 |
